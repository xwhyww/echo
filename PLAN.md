# Echo — план доработок и диагностика voice-задержки

## Контекст

Проект дошёл до состояния, где почти весь заявленный функционал написан: телефонная
авторизация с OTP, личные чаты с шифрованием на диске, друзья, группы с ролями и
инвайтами, голосовые каналы на LiveKit, демонстрация экрана, 1:1 звонки, push-конвейер
на сервере. Задеплоено на один VPS Timeweb в Москве (`72.56.39.133`,
`*.echo-application.ru`) под Caddy.

Две задачи:

1. **Голос работает плохо** — индикатор показывает 200–400 мс. Нужно понять причину.
2. **Составить план** — чего не хватает по функционалу и что стоит доработать сейчас.

Проверено при подготовке: 10 сервисов в `echo-server/services/`, 8 баз Postgres,
NATS JetStream как шина событий, ~190 компонентов и ~90 хуков на клиенте.
Тестов в репозитории нет ни одного, CI нет.

# Часть A. Диагностика voice-задержки

## A.1 Что уже установлено

**Откуда берётся число на экране.** `echo-client/src/lib/stores/voiceStats.svelte.ts:49-51`
раз в 3 секунды дёргает `RTCPeerConnection.getStats()` на publisher-соединении и берёт
`currentRoundTripTime` у номинированной ICE candidate-pair. Показывается в
`echo-client/src/lib/components/voice/ConnectionQualityIndicator.svelte:92`.

Это честный сетевой RTT «клиент ↔ SFU» по STUN-binding. На него **не влияют** ни
локальный аудиоконвейер, ни jitter buffer, ни Opus — то есть 200–400 мс это транспорт,
а не код обработки звука.

**Замеры с машины разработчика** (все — при активном AmneziaVPN, см. ниже):

| Проверка | Результат |
|---|---|
| `ping live.echo-application.ru` | 129 мс среднее, 0% потерь |
| `tracert`, первый хоп | `10.8.1.0` — **89 мс** |
| Активный интерфейс | AmneziaVPN (WireGuard), MTU **1376** |
| Default route | AmneziaVPN, метрика 5 (Ethernet — 25) |
| TCP 443 / 7881 на сервер | открыты |
| TCP 7880 | закрыт — правильно, сигналинг только через Caddy |

**Конфигурация SFU корректна.** `echo-server/deploy/docker-compose.prod.yml` публикует
UDP 50000–50200 и TCP 7881 напрямую с хоста, `use_external_ip: true`, сигналинг 7880
проксируется Caddy на `live.` домене. Медиа через Caddy не идёт. Это правильная схема.

## A.2 Три складывающиеся причины

Ни одна по отдельности не даёт 200–400 мс, вместе — дают.

### Причина 1: география, ~50–70 мс (неустранимо без второго узла)

Новосибирск → Москва по хорошему маршруту это 50–70 мс RTT. Единственный SFU стоит в
Москве, региональной маршрутизации нет. Даже два человека, сидящие рядом в
Новосибирске, гоняют звук через Москву: mouth-to-ear = 2 × RTT + jitter buffer +
буфер вывода, то есть ~150 мс минимум чисто по расстоянию.

### Причина 2 (главный подозреваемый): ICE упал на TCP 7881

Если UDP-диапазон 50000–50200 закрыт в фаерволе Timeweb или в ufw на хосте, LiveKit
молча уходит на TCP-fallback. `currentRoundTripTime` на TCP candidate-pair измеряется
поверх TCP-обёрнутого STUN и раздувается Nagle, ретрансмитами и head-of-line blocking:
путь в 60 мс стабильно читается как 150–400 мс, а звук становится рваным при малейшей
потере пакетов.

**Симптом совпадает точно.** И проверить это сейчас невозможно: код на
`voiceStats.svelte.ts:49` читает из candidate-pair только `currentRoundTripTime`, а
`protocol`, `candidateType` и `relayProtocol` выбрасывает. UI физически не отличает
UDP от TCP.

TURN-сервера в деплое нет вообще, `iceServers` в клиенте не задаются нигде — ICE-серверы
приходят только из ответа сигналинга LiveKit.

### Причина 3: VPN на машине разработчика

AmneziaVPN сейчас активен и перехватывает весь трафик: первый хоп 89 мс до выхода в
интернет. Вы сказали, что при замере 200–400 мс он был выключен — тогда на результат
он не влиял, но **все мои цифры выше сняты через него**, поэтому истинная база
Новосибирск → Москва пока не измерена. Плюс MTU 1376 против обычных 1500: при
демонстрации экрана это фрагментация и потери.

## A.3 Что сделать — по порядку

### ~~Шаг 1. Показать транспорт в индикаторе~~ — СДЕЛАНО

Без этого дальше гадать. В `voiceStats.svelte.ts` в цикле `report.forEach` рядом с
чтением RTT забрать ещё и тип пары:

- сохранить `stat.localCandidateId` / `stat.remoteCandidateId` номинированной пары;

- добавить в стор `transport` и `candidateType` рядом с `latencyMs`.

Вывести в поповере `ConnectionQualityIndicator.svelte:110` строкой «UDP · host» /

**Если там TCP — причина найдена, переходим к шагу 2. Если UDP — к шагу 3.**

### Шаг 2. Открыть UDP-диапазон (15 мин)

На сервере:

```bash
ufw status numbered | grep -E '50000|7881'
docker compose -f docker-compose.prod.yml port livekit 50000/udp
```

Плюс security group в панели Timeweb — она отдельно от ufw. Нужно
`50000:50200/udp` и `7881/tcp`, как описано в `echo-server/deploy/README.md`.
Осторожно: Docker пишет свои правила iptables **впереди** ufw, поэтому «ufw закрыт» и
«порт недоступен» — не одно и то же; проверять снаружи, например
`nc -u -v -z <ip> 50000` при активном звонке.

### Шаг 3. Замерить базу честно (15 мин)

С выключенным AmneziaVPN: `ping 72.56.39.133` и `tracert`. Это даёт нижнюю границу.
Если база 60 мс, а индикатор показывает 250 — проблема в транспорте (шаг 2).
Если база сама 200 — проблема у провайдера/маршрута, и лечится только вторым узлом.

Отдельно стоит добавить исключение для `72.56.39.133` в split-tunnel Amnezia, чтобы
трафик Echo ходил мимо VPN — иначе в разработке вы всегда будете видеть +90 мс.

## B.1' Android push вместо Apple

- `push-service/src/fcm.ts` — клиент FCM HTTP v1 без `firebase-admin`: обмен
  service-account JWT на access token и один POST. Легаси-API со статическим
  ключом отключён в 2024, поэтому нужен именно этот путь.
- `sender.ts` выбирает провайдера по `platform` строки устройства. Провайдеры
  независимы: Android может работать, пока APNs ждёт оплаты Apple.
- Нативный плагин: `plugins/push/android/` (Gradle + Kotlin `PushPlugin.kt`),
  `src/android.rs`. Разрешение POST_NOTIFICATIONS появилось только в Android 13,
  ниже `requestPermission` отвечает true без диалога. Компилируется под
  `aarch64-linux-android`.
- Новая команда `platform` отвечает из Rust через `cfg!` — Swift не тронут.
- `scripts/android.mjs` дописывает в генерируемый Gradle-проект плагин
  Google Services и копирует `google-services.json`. Без файла ничего не
  патчится, и это корректное состояние до создания Firebase-проекта.

**От вас нужно:** проект в Firebase → `google-services.json` в `src-tauri/`
и service-account JSON в `echo-server/deploy/fcm/`, плюс
`FCM_SERVICE_ACCOUNT_PATH` в `.env`.

## B.4 оказался шире, чем записано

TODO в `presence.ts` описывал утечку идентификаторов участников. Рядом нашлось

## B.5 и то, что вскрылось по дороге

Логика шифрования вынесена в `@echo/shared/crypto` (`messageRow.ts`), чтобы не
заводить третью копию, и покрыта тестами. Применена к `groups-service` и
`voice-service`: колонки, миграции, шифрование на запись, расшифровка на чтение,
`attachments_meta` для SQL-запросов по медиа, скрипты бэкфилла.

Два дефекта в существующем коде, найденные при этом:

1. **Миграции groups-service ломали деплой.** 0001–0003 написаны вручную, а
   snapshot'ы drizzle не обновлялись — `db:generate` предлагал заново добавить
   уже существующие колонки. Миграции применяются при старте контейнера, то есть
   следующий деплой упал бы. Исправлено: `0004` содержит только новые колонки,
   snapshot приведён в соответствие.
2. **Бэкфилл pers-chats не очищает открытый текст.** Он пишет шифротекст, но
   оставляет `content`, `attachments` и `reply_to_snapshot` на месте — после
   прогона старые сообщения лежат в базе дважды, и приватности не прибавляется.
   Мои скрипты для групп и голосовых каналов очищают. **pers-chats нужно
   починить отдельно** — это не входило в задачу.

## A.3 шаг 5 — конфигурация готова, разворачивать нечего

`deploy/docker-compose.multiregion.yml` превращает текущий LiveKit в первый
узел кластера, `deploy/docker-compose.sfu-node.yml` + `Caddyfile.sfu-node` —
весь стек для второй машины.

**Что проверено на самом деле:** два контейнера `livekit-server:1.11.0` подняты
против одного Redis — оба зарегистрировались (`redis-cli hlen nodes` = 2), у
каждого свой регион в логе. Затем слитый продовый конфиг скормлен контейнеру
дословно: стартует, `"region":"moscow"`, диапазон ICE верный. **Не проверено:**
вторая машина, сеть между ними, реальный звонок через регионы.

Ключевое: попадание в кластер само по себе задержку не снижает — комната
привязывается к узлу при создании, и новосибирец в московской комнате всё равно
шлёт пакеты в Москву. Работает `node_selector.kind: regionaware`, который
выбирает узел в ближайшем к клиенту регионе. Поэтому у каждого узла свой
`region:`, а список `regions` обязан совпадать на всех узлах.

Неприятная часть — общий Redis: сейчас он виден только внутри docker-сети, а
второму узлу нужен тот же. Публиковать порт нельзя. Варианты по убыванию
предпочтительности — приватная сеть Timeweb, WireGuard между хостами,
`requirepass` + TLS + allowlist. Подробности в `deploy/README.md`.

## A.3 шаг 4, пункты 2–4 — что выяснилось

**Пункт 2 — параллельный граф в `remoteAudio.ts` оставлен, и строка таблицы
про «лишний буфер» была неверной.** Проверено по исходникам livekit-client
2.18: `webAudioMix: true` строит ровно тот же граф — прикрепляет элемент,
ставит ему `volume = 0` и `muted = true`, дальше
`createMediaStreamSource → GainNode → destination` на контексте, который сам
открывает с `latencyHint: 'interactive'`. То есть параллельного графа нет ни
в одном из вариантов: один заглушённый элемент кормит один gain-узел, один хоп
WebAudio, одинаковая задержка. Менять свои 165 строк, где записана причуда
декодера Chromium, на чужие ради нуля миллисекунд и изменения поведения
«заглушить» — не стоит. Единственное, чего SDK умеет больше, — `setSinkId`
для выбора устройства вывода; выбора устройства вывода в Echo нет. Разбор
записан в шапке `remoteAudio.ts`, чтобы вопрос не открывали заново.

**Пункт 3 — цена DFN3 и VAD-гейта теперь видна в UI.** Каждый включённый
тумблер на `/profile/audio` подписан тем, сколько миллисекунд он добавляет
(RNNoise ≈10, DeepFilterNet ≈40, VAD-гейт ≈50: ~30 на решение модели плюс 20 на
`RAMP_OPEN_S`), а над списком стоит общая сумма. RNNoise в сумму не входит,
когда включён DeepFilterNet, — `captureMic` выбирает один из двух.

**Пункт 4 — `publishDefaults` заданы явно**, общим объектом
`lib/voice/roomOptions.ts` для голосовых каналов и для звонков 1:1.
`dtx: false` (иначе кодек молчит в паузах и джиттер-буфер раскручивается
заново на каждой фразе — тот же съеденный первый слог, что и у VAD-гейта; в
Echo уже есть VAD-гейт для тех, кому нужно подавление тишины), `red: true`
и `audioPreset: AudioPresets.music` — закреплены, чтобы не зависеть от версии
SDK. Видео оставлено SDK: единственное видео здесь — шаринг экрана, и он
задаёт своё кодирование при публикации.

# Проверка результата

**Голос (после шагов 1–3).** Зайти в голосовой канал с двух устройств, открыть
поповер индикатора качества. Ожидается «UDP · host» и RTT, близкий к `ping` без VPN
(Новосибирск → Москва: 50–70 мс). Если после открытия UDP надпись сменилась с TCP на
UDP и цифра упала — причина была в фаерволе. Параллельно `chrome://webrtc-internals`
показывает выбранную candidate-pair независимо от нашего кода — это контрольный замер.

**Задержка (после шага 4).** Субъективно — разговор вдвоём: пропадает эффект
«перебиваем друг друга». Объективно — записать оба конца и измерить сдвиг; либо
`AudioContext.baseLatency` + `outputLatency` до и после.

**Rate limiting.** Скриптом отправить 20 запросов `POST /auth/otp/request` на один
номер: со второго-третьего должен идти `429`. Проверить, что нормальный вход не
сломался и повторная отправка кода через минуту работает.

**Интеграционные тесты.** Поднять базу и прогнать их против неё:

```bash
cd echo-server
pnpm infra:up
docker compose exec postgres createdb -U echo echo_groups_test
TEST_DATABASE_URL=postgresql://echo:echo_dev@localhost:15432/echo_groups_test pnpm test
```

Без переменной набор пропускается — «4 passed | 1 skipped». С ней должно быть
пять файлов и ни одного skipped. В CI базу даёт service-контейнер.

**Сбор логов.** `docker compose -f docker-compose.prod.yml -f docker-compose.logging.yml up -d`,
затем через SSH-туннель `curl -sG http://127.0.0.1:3100/loki/api/v1/query_range
--data-urlencode 'query={stack="echo"}'` — должны идти строки со всех десяти
сервисов, с метками `service` и `level`.

**Регрессии в клиенте.** `npm run check` — база 1 error / 0 warnings, рост считать
поломкой. `npm run build` должен проходить целиком, включая prerender-обход.

**Сервер.** `docker compose -f docker-compose.prod.yml ps` — все контейнеры healthy,
`curl https://api.echo-application.ru/health` отвечает `{"status":"ok"}`.
